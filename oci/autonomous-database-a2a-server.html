Autonomous AI Database の A2A 連携と対応エージェント

Autonomous AI Database に、マネージドの Agent2Agent (A2A) サーバーが組み込まれました。Select AI Agent フレームワークで作ったエージェントチームを A2A プロトコルで公開でき、外部の A2A 対応エージェントが標準の HTTPS 経由でそれを発見し、呼び出せます。A2A サーバー用のインフラを別途立てる必要はありません。

Oracle が公式に例示している接続先は Google Gemini Enterprise、Azure AI Foundry、Microsoft Copilot Studio、および A2A に対応した独自アプリケーションです。対応するデータベースバージョンは 19c と 26ai、デプロイ形態は Serverless と Dedicated Region で、ADB@Azure / ADB@GCP / ADB@AWS でも使えます。

何が新しいのか

Autonomous AI Database には以前から Select AI Agent という「データベース内で動く AI エージェント」の仕組みがあります。DBMS_CLOUD_AI_AGENT パッケージでエージェント、タスク、ツール、そしてそれらを束ねたチーム (agent team) を定義し、ReAct パターンで推論とツール呼び出しを回すものです。エージェントのロジックもデータアクセスもデータベースの中で完結するのが特徴でした。

これまでは、その中のエージェントを外部のアプリケーションから使うたびに、個別の連携コードを書く必要がありました。今回追加された A2A サーバーは、そこを標準プロトコルに置き換えます。Oracle 側がサーバーの可用性・ライフサイクル・運用を管理するフルマネージドかつマルチテナントの機能としてデータベースに埋め込まれているので、利用者はサーバーを構築も運用もしません。

A2A は Google が公開したエージェント間通信のオープン標準です。異なるフレームワークで作られたエージェント同士が、エージェントの自己紹介にあたる Agent Card を通じて互いの能力を知り、JSON-RPC over HTTPS で会話します。Autonomous AI Database はこの標準の「サーバー側」を担うことになった、と理解すると分かりやすいです。

全体像

外部クライアントから見ると、流れは A2A の標準的なパターンそのものです。利用可能なエージェントを一覧し、Agent Card を取得し、承認されたエージェントを呼び出します。呼び出しの先ではデータベース内の Select AI Agent が動き、データはデータベースの外に出ません。

対応しているエージェント

Oracle のドキュメントが接続先の例として挙げているのは次の 3 製品と、独自実装です。いずれも「A2A プロトコルに対応したクライアント」であることが条件なので、この 3 つだけに限定されるわけではありません。逆に言えば、A2A に対応していないツールは対象外です。

  • Google Gemini Enterprise: Oracle AI Database Agent という形で提供され、Google Cloud Marketplace から入手してから Gemini Enterprise 側で構成します。Agent Development Kit (ADK) を使えば、分析・可視化・文書生成といった役割の異なるエージェントを組み合わせたワークフローにも組み込めます。
  • Azure AI Foundry: Microsoft のエージェント開発基盤から、A2A 経由でデータベース内エージェントを呼び出します。
  • Microsoft Copilot Studio: 業務ユーザー向けの Copilot に、データベース内エージェントを一つの相手先エージェントとして組み込めます。

ここで重要なのは、接続先が増えてもデータベース側の作り込みは変わらない点です。エージェントチームを一度 A2A で公開してしまえば、あとはクライアントごとの個別連携ではなく、共通のプロトコルで発見と呼び出しが行われます。

有効化の手順

1. フリーフォームタグで A2A サーバーを有効化

OCI コンソールの Autonomous AI Database 詳細画面から「タグの管理」を開き、フリーフォームタグを追加します。タグキーは adb$feature で、値に有効化したい機能を JSON で指定します。タグを更新するので、操作する OCI ユーザーにはデータベースを更新する IAM 権限が必要です。

# タグキー
adb$feature

# タグ値（A2A サーバーを有効化）
{"name":"a2a_server","enable":true}

MCP サーバーと A2A サーバーは独立して有効化します。片方を有効にしても、もう片方には影響しません。注意点として、1 つのタグに複数の name/value を配列でまとめて指定することはできません。両方使いたい場合はタグを分けて追加します。

# MCP サーバーを併用する場合は、別のタグとして追加する
{"name":"mcp_server","enable":true}

2. エージェントチームを用意する

公開する対象は個々のエージェントではなくエージェントチームです。Select AI Agent フレームワークでエージェント、タスク、ツールを定義し、チームにまとめます。データベースユーザーには DBMS_CLOUD_AI_AGENT の実行権限に加え、Select AI が要求する権限一式が必要です。

3. 認証を設定してクライアントを接続する

認証は組織の ID 基盤に合わせて設定します。データベース資格証明から Bearer トークンを生成する方法が基本で、トークンエンドポイントは /adb/auth/v1/databases/{database-ocid}/token です。取得したトークンはリクエストヘッダーに付けて送ります。トークンの有効期間はおよそ 1 時間なので、常時稼働するクライアントでは期限前の再取得を実装しておきます。

Authorization: Bearer <token>

より本格的な構成では、Oracle Database Identity、OCI IAM、外部の OIDC / OAuth 2.1 との連携を使い、認証と認可を全社の ID 基盤に寄せられます。Gemini Enterprise 向けの Oracle AI Database Agent は OAuth 2.0 のパスワードグラントを使い、データベースのユーザー名とパスワードからトークンを取得する実装になっています。

セキュリティとガバナンス

A2A サーバーがデータベースに統合されていることの実利は、既存の統制がそのまま効く点にあります。アクセス制御リスト、ユーザー権限、Virtual Private Database (VPD) ポリシーによる行レベルの制御、監査ログ、レート制限が、外部エージェントからの呼び出しにも適用されます。エージェントが参照できるデータの範囲は、そのエージェントが動くデータベースユーザーの権限で決まります。

エージェントのロジックとデータアクセスをデータベース側に置いたまま、外部にはプロトコルの口だけを開ける構成なので、業務データを外部のエージェント基盤へコピーせずにマルチエージェント構成へ参加できます。ADB@Azure / ADB@GCP / ADB@AWS といったマルチクラウド環境でも同じ統制を維持できる、というのが Oracle の主張です。
