Babelfish for Aurora PostgreSQL の T-SQL 互換性はどう担保されるのか

Babelfish は SQL Server の実装を移植したものではありません。Aurora PostgreSQL に「T-SQL 方言のレイヤ」を足すことで互換性を作っています。具体的には ① SQL Server の TDS ワイヤプロトコルを話す追加 endpoint (port 1433)、② T-SQL の方言・データ型・sys.* カタログビュー・stored procedure・cursor・trigger を再実装した言語レイヤ、③ PostgreSQL のエラーを SQL Server 相当の error code に写し替えるマッピング層、という 3 層構造です。

そして重要なのは、互換性が「100% 保証」されるものではない点です。AWS が担保しているのは「その Babelfish バージョンがサポートすると明記した範囲」であり、それはバージョンごとの対応表・差異表・非サポート一覧としてドキュメント化されています。残りの差分は、移行前の Babelfish Compass によるアセスメントと、未サポート構文を受け流す escape hatch、そして PostgreSQL 側の構文への書き換えで埋める運用になります。

互換性を作っている 3 つのレイヤ

AWS のドキュメントは Babelfish を「TDS ポート経由で T-SQL 方言を使い、PostgreSQL の上に T-SQL のセマンティクスを提供するよう設計されたもの」と説明しています。レイヤごとに何を担保しているのかを分けて見ると、どこまで信用できるかが判断しやすくなります。

① ワイヤプロトコル層 — ドライバを替えずに繋がる

Babelfish は Aurora PostgreSQL クラスタに追加の endpoint を提供し、SQL Server のワイヤレベルプロトコル (TDS: Tabular Data Stream) を解釈します。サポート対象は TDS 7.1〜7.4 で、クライアントはデフォルトで port 1433 に接続します。PostgreSQL 方言 (PL/pgSQL) 側は従来どおり port 5432 です。つまりアプリ側の接続文字列とドライバはそのままで、接続先だけを差し替えられます。これが「few code changes で動く」と言われる根拠の一番下の層です。

ただしプロトコル層にも例外があります。MSDTC (Microsoft Distributed Transaction Coordinator) に関連する接続属性を使う API リクエストは未サポートで、SQL Server JDBC ドライバの SQLServerXAResource による XA 呼び出しも含まれます。また、Microsoft JDBC ドライバの代替である OSS の jTDS ドライバはサポート対象外です。

② 言語・オブジェクト層 — T-SQL の「見た目」を再現する

Babelfish を有効にしてクラスタを作成すると、Aurora は babelfish_db という名前の PostgreSQL データベースをプロビジョニングします。移行された SQL Server のオブジェクトと構造はすべてこの中に入ります。TDS ポートに接続したセッションは自動的に babelfish_db に置かれ、T-SQL から見ると SQL Server インスタンスに繋いだのと同じ構造、つまり master / msdb / tempdb と sys.databases カタログが見えます。ユーザーデータベースを追加して USE で切り替えることもできます。SQL Server のユーザーデータベースは babelfish_db の中に flatten されますが、クロスデータベースの構文とセマンティクスは SQL Server と同等か近いものが維持されます。

互換性の対象になる要素は、SQL 方言そのものに加えて cursor、カタログビュー、データ型、trigger、stored procedure、function にまで及びます。だからこそ、既存の T-SQL をほぼそのまま動かせます。

babelfish_db という名前は Babelfish 用に予約されています。自分で同名のデータベースを作ると、Aurora が Babelfish を正常にプロビジョニングできなくなるので注意してください。

③ エラー・セマンティクス層 — 失敗の仕方まで寄せる

互換性は「成功するクエリ」だけの話ではありません。アプリケーションはエラーコードで分岐するので、失敗の仕方も揃っている必要があります。Babelfish は制御フローとトランザクション状態について可能な限り SQL Server の振る舞いを再現し、エラー時には SQL Server のエラーコードに近いコードを返します。マッピングできない場合は固定の 33557097 を返し、エラー種別ごとに次の動作をとります。

  • コンパイル時エラー: トランザクションをロールバックする
  • 実行時エラー: バッチを終了し、トランザクションをロールバックする
  • クライアントとサーバー間のプロトコルエラー: トランザクションはロールバックしない

同等のコードがない場合は、似たエラーのコードへ寄せられます。たとえば SQL Server のコード 8143 と 8144 を引き起こす振る舞いは、どちらも 8143 にマップされます。ここは実務上とても重要な落とし穴があり、マップできないエラーは TRY...CATCH を尊重しません。SQL Server 側で TRY...CATCH に頼ってリトライしている処理は、個別に挙動を確認してください。

調査には次の関数が使えます。

-- SQL Server 互換のエラーコード
SELECT @@ERROR;

-- 元の PostgreSQL エラーコード
SELECT @@PGERROR;

-- マッピング済みエラーコードの一覧
SELECT * FROM fn_mapped_system_error_list();
GO

「どこまで担保されるか」はバージョンで決まる

Babelfish は Aurora PostgreSQL 13.4 で最初に提供され、それ以降リリースごとに機能が追加されている進化中の機能です。AWS 自身が「最新バージョンにおける SQL Server の T-SQL と Babelfish の T-SQL の差異を理解しておくことを推奨する」と明記しており、互換性の担保は固定の仕様ではなく「バージョンごとのサポート表」として提供されています。参照すべきドキュメントは 3 つに分かれています。

  • Supported functionalities in Babelfish by version: T-SQL 構文・関数・SERVERPROPERTY のプロパティなどが、どのバージョンから Yes になったかのマトリクス
  • T-SQL differences in Babelfish: 動くけれども SQL Server と挙動が違うもの
  • Unsupported functionalities in Babelfish: そもそも動かないもの

したがって最初にやるべきことは、自分のクラスタの Babelfish バージョンを確定させることです。

-- TDS ポート (1433) に接続して確認
SELECT CAST(SERVERPROPERTY('babelfishversion') AS VARCHAR);
GO
-- 例: 3.4.0

SELECT aurora_version() AS aurora_version;
GO
-- 例: 15.5.0

SELECT @@VERSION AS version;
GO
-- 例: Babelfish for Aurora PostgreSQL with SQL Server Compatibility - 12.0.2000.8

-- Babelfish 上かどうかの判定(Babelfish は 1、SQL Server は NULL を返す)
SELECT SERVERPROPERTY('Babelfish');
GO

リージョンで Babelfish が使える Aurora PostgreSQL バージョンは、AWS CLI でも引けます。

aws rds describe-db-engine-versions --region ap-northeast-1 \
  --engine aurora-postgresql \
  --query '*[]|[?SupportsBabelfish==`true`].[EngineVersion]' \
  --output text

なお、クライアントツールやドライバが SQL Server のバージョン番号で機能を判定してくる場合に備えて、返す製品バージョンを DB クラスタパラメータ babelfishpg_tds.product_version で変更できます。これは @@VERSION、SERVERPROPERTY('ProductVersion')、PRELOGIN レスポンスの VERSION トークン、JDBC の DatabaseMetaData.getDatabaseProductVersion() が返す値に効きます(前 2 つは即時、後 2 つは新規セッションから)。

aws rds modify-db-cluster-parameter-group \
  --db-cluster-parameter-group-name mydbparametergroup \
  --parameters "ParameterName=babelfishpg_tds.product_version,ParameterValue=15.2.4000.1,ApplyMethod=immediate"

比較のセマンティクスは collation で担保される

T-SQL 互換性で見落としやすいのが文字列比較です。SQL Server は既定で大文字小文字を区別しない比較をしますが、PostgreSQL は区別します。ここは collation パラメータで埋められています。

  • babelfishpg_tsql.server_collation_name: サーバーとデータベースの既定 collation。デフォルトは sql_latin1_general_cp1_ci_as。T-SQL ではサーバー collation が識別子の比較方法を決めるため、この値は CI_AS (大文字小文字を区別しない・アクセントを区別する) でなければなりません。Babelfish データベース作成後に変更してはいけません
  • babelfishpg_tsql.default_locale: collation が使う既定ロケール。デフォルトは en-US。既存クラスタでこの値を変えても、既存 collation のロケールには影響しません

これらはクラスタ作成時に選んだ値が DB クラスタパラメータグループに保存されます。使える collation の一覧は T-SQL から確認できます。

SELECT * FROM fn_helpcollations();
GO

未サポート構文の受け流し: escape hatch

既存の T-SQL には、Babelfish に実装がない構文が混ざるのが普通です。そこで Babelfish は escape hatch という仕組みを持っています。これは「未サポートの機能や構文に遭遇したときの振る舞い」を指定するオプションで、ignore (受理して無視) か strict (エラーを返す) を選べます。設定は sp_babelfish_configure で行います。

-- 全 escape hatch と現在値・使い方を一覧
EXECUTE sp_babelfish_configure;
GO

-- 名前で絞って確認(ワイルドカード可)
EXECUTE sp_babelfish_configure 'escape_hatch_query_hints';
GO

-- クラスタ全体に恒久的に設定する場合は 'server' を付ける
EXECUTE sp_babelfish_configure 'escape_hatch_unique_constraint', 'ignore', 'server';
GO

-- 既定値に戻す(Babelfish 1.2.0 以降)
EXECUTE sp_babelfish_configure 'default';
GO

既定値は項目ごとに異なります。代表的なものを挙げます。

  • escape_hatch_index_clustering (既定 ignore): CLUSTERED / NONCLUSTERED キーワードを制御します。CLUSTERED が無視された場合、インデックスや制約は NONCLUSTERED 指定だったものとして作成されます
  • escape_hatch_query_hints (既定 ignore): OPTION (...) 句のクエリヒントを無視します
  • escape_hatch_table_hints (既定 ignore) / escape_hatch_join_hints (既定 ignore): WITH (...) のテーブルヒント、JOIN の LOOP / HASH / MERGE などを無視します
  • escape_hatch_storage_options (既定 ignore): ON [PRIMARY]、TEXTIMAGE_ON、FILESTREAM_ON といったストレージ指定句を無視します
  • escape_hatch_rowversion (既定 strict) / escape_hatch_storage_on_partition (既定 strict): それぞれ ROWVERSION / TIMESTAMP データ型、ON partition_scheme (column) によるパーティション指定を制御します。Babelfish はパーティショニングを現時点で実装していません
  • escape_hatch_index_columnstore (既定 strict): ignore を指定すると、columnstore ではなく通常の B-tree インデックスが作られます

ここで必ず意識しておきたいのは、ignore は「意味を実現した」のではなく「構文を受理して捨てた」だけであるという点です。CLUSTERED が NONCLUSTERED になり、クエリヒントは効かず、ファイルグループ指定は消えます。DDL はエラーなく通るので移行作業は進みますが、物理設計とプラン制御の意図はそこで落ちています。性能面は escape hatch とは別に、移行後に実測で確認するという前提を置いてください。

担保されない部分 — 代表的な非サポートと挙動差

「どう担保されるか」の裏側として、担保されないものを把握しておく方が実務では重要です。公式の非サポート一覧から、移行判断に効きやすいものを抜き出します。

機能として動かないもの

  • Assembly モジュールと SQL CLR ルーチン(外部定義の function / procedure / trigger を含む)
  • DBCC コマンド(Babelfish 3.4.0 以降の DBCC CHECKIDENT は例外としてサポート)
  • Temporal tables、Materialized views、Row-level security (CREATE SECURITY POLICY)、Service Broker、SQL graph 機能
  • グローバル一時テーブル(## で始まる名前)
  • 更新可能カーソル、GLOBAL カーソル、FETCH PRIOR / FIRST / LAST / ABSOLUTE / RELATIVE、SCROLL / KEYSET / DYNAMIC / FAST_FORWARD などのカーソルオプション
  • EXECUTE AS 文、function / procedure / trigger 内の EXECUTE AS SELF / EXECUTE AS USER 句
  • 複数データベースにまたがるオブジェクトを操作するクロスデータベース DDL
  • xp_cmdshell などの拡張ストアドプロシージャ、SP_CONFIGURE
  • BACKUP / RESTORE DATABASE、DAC パッケージ (.dacpac / .bacpac) の import / export、可用性グループ関連の DDL
  • 名前に @ や角かっこを含むテーブル名・列名、インラインインデックス、変数に入れた名前でのプロシージャ呼び出し、パラメータ 100 個超の宣言

動くが挙動が違うもの

  • @@version が返す値の書式が SQL Server と少し違います。書式に依存したコードは壊れます
  • ALTER TABLE は 1 列または 1 制約の追加・削除のみサポートします
  • ALTER TABLE..ALTER COLUMN では NULL / NOT NULL を指定できません。null 許容性を変えるには PostgreSQL の ALTER TABLE..{SET|DROP} NOT NULL を使います
  • 集計関数は部分サポートです(AVG、COUNT、COUNT_BIG、GROUPING、MAX、MIN、STRING_AGG、SUM がサポート対象)
  • 文字列・16 進文字列の行継続文字(改行直前のバックスラッシュ)は未サポートです。文字列では文字として解釈され、16 進文字列では構文エラーになります
  • リモートオブジェクト参照は読み取り限定です。linked server に対するストアドプロシージャの実行はサポートされず、4 部構成のオブジェクト名は読み取りでのみ動作し、リモートテーブルの更新はできません

Aurora 側の機能制限

T-SQL とは別に、Babelfish を有効にすると使えなくなる Aurora 機能があります。設計段階で効いてくるので無視できません。

  • IAM データベース認証、Database Activity Streams (DAS)、RDS Data API、RDS Proxy、SCRAM、Query editor、Zero-ETL 統合、Iceberg / Parquet データのクエリ
  • 未サポートの PostgreSQL 拡張: pgcrypto、hstore、ltree、citext、cube、bloom、btree_gin、btree_gist、hypopg、pglogical による論理レプリケーション、apg_plan_mgmt によるクエリプラン管理

実務での担保手順: Babelfish Compass による事前アセスメント

ここまでの内容は裏を返すと「自分のコードがサポート範囲に入っているかは、自分で測るしかない」という話になります。AWS の移行手順でも、DDL を出してアセスメントツールを走らせる工程が明示的に組まれています。

手順の骨格は次のとおりです。

  1. 移行元 SQL Server から DDL を出力する。SSMS の Generate Script Wizard で「Script entire database and all database objects」を選び、単一スクリプトファイルとして保存します。Advanced では既定で false になっている項目を true に変えておくと漏れが減ります(Script Change Tracking / Full-Text Indexes / Triggers / Logins / Owner / Object-Level Permissions / Collations)
  2. その DDL を Babelfish Compass にかけ、T-SQL のどこまでが現行 Babelfish でサポートされるかを判定する
  3. Babelfish を有効にした Aurora PostgreSQL クラスタを作成する
  4. DDL を適用し(まずはスキーマ・ユーザー定義型・主キー付きテーブルのみ)、AWS DMS でデータを移行する
  5. アプリケーションを TDS endpoint に向けて回帰テストする
# Babelfish Compass の実行例(Windows)
C:\BabelfishCompass> BabelfishCompass.bat YourFirstReportName test\school-sample-db.sql

Compass の判定は、インストールディレクトリにある BabelfishFeatures.cfg が元データです。このファイルは Babelfish のリリースごとに更新されるため、アセスメントは「どの Babelfish バージョンに対しての判定か」とセットでしか意味を持ちません。レポートでは検出項目が Not Supported / Review Semantics / Review Performance / Review Manually / Ignored に分類され、解消にかかる手間の目安として complexity score (LOW / MEDIUM / HIGH) が付きます。これが移行プロジェクトの go / no-go 判断材料になります。

なお Babelfish Compass は Babelfish 製品の一部ではありますが、技術的には Babelfish 本体およびそのコードから分離されたスタンドアロンかつオープンソースのツールで、別の GitHub リポジトリに置かれています。問題を見つけた場合は AWS Support ではなく GitHub に報告するよう案内されています。

PostgreSQL 側と併用するときの注意

babelfish_db は PostgreSQL の標準ポートからも PostgreSQL の SQL 文でアクセスできます。段階的に PostgreSQL ネイティブへ移行していく上では便利ですが、本番で両方を同じアプリケーションコンテキストから使う場合、AWS は相互運用性の問題を事前に検討するよう強く推奨しています。干渉しうるポイントとして挙げられているのは、スキーマ名、識別子、権限、トランザクションセマンティクス、複数結果セット、既定 collation などです。Babelfish の新バージョンがリリースされた際に、構文・セマンティクス・互換性へ影響が出る可能性もあると明記されています。

スキーマ名については migration mode の選択が直接効いてきます。

  • single-db モード: SQL Server のスキーマ名が babelfish_db の中でもそのまま維持されます。PostgreSQL からも SQL Server と同じ名前で参照できるため、将来 PostgreSQL ネイティブへ完全移行する前提ならこちらが有利です
  • multi-db モード: PostgreSQL から見たユーザーデータベースのスキーマ名が dbname_schemaname になります(例: dba の dbo と dev は dba_dbo / dba_dev)。T-SQL から見た名前は変わりません。同一インスタンスに複数ユーザーデータベースを持つ SQL Server 的な使い方をしたい場合はこちらです

この migration mode は migration_mode パラメータに保存されます。クラスタ作成後に変更してはいけません。変更すると、それまでに作成した SQL オブジェクトすべてへのアクセスを失う可能性があります。

もう一点、SQL Server と違い Babelfish はクラスタ再起動後に tempdb を再初期化しません。システムデータベース (master / tempdb) 内にオブジェクトを作成・変更していた場合は、新クラスタ側で作り直す必要があります。

まとめ: 「担保」の正体

Babelfish の T-SQL 互換性は、次の 4 点の組み合わせで成立しています。

  1. プロトコルとオブジェクトモデルの再実装: TDS endpoint、T-SQL 方言、sys.* カタログ、SQL Server 互換のデータ型・procedure・cursor・trigger
  2. 失敗の互換: SQL Server error code へのマッピングと、マップできない場合の固定コード 33557097
  3. サポート範囲のドキュメント化: バージョン別対応表・差異表・非サポート一覧として明示される
  4. 差分を埋める運用: Babelfish Compass による事前アセスメント、escape hatch による構文の受理、PostgreSQL 構文への部分的な書き換え

したがって「Babelfish を使えば T-SQL が全部そのまま動く」という読み方は誤りです。正しくは「ドキュメント化されたサポート範囲については互換的に動き、範囲外は事前に検出して個別に対処する」仕組みが担保されている、という整理になります。移行判断の実務では、まず自分のクラスタの Babelfish バージョンを固定し、そのバージョンの対応表に対して Compass をかける、という順序を崩さないことが肝心です。
