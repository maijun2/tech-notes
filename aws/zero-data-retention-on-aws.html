Claude Opus 5 on AWS の ZDR (Zero Data Retention) とは

ZDR は Zero Data Retention の略で、推論に使ったプロンプトと応答を、API レスポンスを返した後にサーバー側へ保存しないという取り決めです。「データを保持し続けない」という理解で合っています。ただし ZDR は「データを送らない」ことではありません。推論のためにデータは確実に送られ、処理された後に残さない、という約束です。

もうひとつ大事なのが、誰が保持しないのかが利用経路で変わる点です。Amazon Bedrock では AWS がデータ処理者で、Anthropic は推論の入出力を保持しません。Anthropic の ZDR プログラムはそもそも Bedrock には適用されず、保持の制御は Bedrock 側の機能で行います。一方 Claude Platform on AWS と第一者の Claude API では Anthropic がデータ処理者で、ZDR は組織単位の申請ベースで有効化します。

ZDR の定義は「レスポンス後に at rest で残さない」

Anthropic の公式ドキュメントは ZDR をこう定義しています。

Under a ZDR arrangement, Anthropic does not store customer prompts or responses at rest after the API response is returned.

キーワードは at rest(保存された状態)と after the API response is returned(レスポンスを返した後)の 2 つです。推論中はメモリ上でデータを扱いますし、リクエストがネットワークを流れることも当然あります。ZDR が保証するのは、そこから先にディスクへ落として持ち続けないことです。

学習利用の話とも切り分けて考えてください。Anthropic は ZDR の有無にかかわらず、保持したデータを明示的な許可なしにモデルの学習へ使わないと明記しています。ZDR は「学習に使わせない仕組み」ではなく「そもそも残さない仕組み」です。

経路によってデータ処理者が違う

質問の元記事は Claude Opus 5 が AWS で使えるようになったという発表で、Bedrock と Claude Platform on AWS の両方に触れています。この 2 つは同じ AWS 経由でも、データの扱いがまったく別物です。

Anthropic のドキュメントは、Bedrock について「zero operator access」、つまり Anthropic の人員が推論基盤にアクセスできないと明記しています。移行ガイドの警告文も直球です。

On Bedrock, AWS is the data processor and Anthropic does not retain inference inputs or outputs. Anthropic's ZDR program does not apply there.

Bedrock から Claude Platform on AWS へ移す場合、「AWS で使っているから今までどおり」とはなりません。Claude Platform on AWS では ZDR が opt-in なので、データ保持の保証に依存する本番ワークロードを移す前に、有効化されているかを Anthropic の担当者に確認する必要があります。

ちなみに Bedrock 上の Claude Opus 5 のモデル ID は anthropic.claude-opus-5 で、エンドポイントは次の形です。

https://bedrock-mantle.us-east-1.api.aws/anthropic/v1/messages

ZDR でも消えないものがある

ここが実務で効いてくる部分です。ZDR は万能の消去装置ではありません。

まず、法令上の要請がある場合と、Anthropic の自動 trust and safety システムがフラグを立てた場合です。この場合、ZDR や HIPAA の取り決めがあっても、入出力を最大 2 年間保持することがあります。

次に、機能を動かすために最小限の技術的な痕跡を残すものがあります。ドキュメントではこれを「Yes (qualified)」と表記していて、プロンプトと応答そのものは保存しないが、限定的なデータは短時間だけ残る、という意味です。

  • prompt caching は KV cache と暗号学的ハッシュをキャッシュの TTL のあいだメモリに保持し、期限切れ後に削除します
  • structured outputs と strict: true のツール定義は、JSON スキーマだけを最終使用から最大 24 時間キャッシュします(だから PHI をスキーマ名や enum 値に入れてはいけません)
  • cache diagnostics はハッシュとトークン数見積もりのフィンガープリントを短時間だけ保持します

ZDR の対象外になる機能

そもそも状態を持つ機能は ZDR にできません。ジョブやファイルやコンテナを保存することが機能の前提だからです。

  • Files API は明示的に削除するまでファイルを保持します
  • Message Batches は 29 日保持します
  • code execution とその上に立つ programmatic tool calling は、コンテナのデータを最大 30 日保持します
  • Claude Managed Agents はセッションの transcript を削除するまで保持します

注意したいのは、ZDR 組織がこれらを呼んでもエラーにならない点です。HIPAA readiness では非対応機能を含むリクエストが 400 で弾かれますが、ZDR はブロックしません。使った時点で、そのデータについては ZDR の外に出る選択をしたことになり、その機能のポリシーが適用されます。

製品単位で対象外になるものもあります。Claude Console と Workbench、Claude Free / Pro / Max などの消費者向けプラン、Claude Teams と Claude Enterprise のインターフェース(例外は ZDR 有効な Enterprise 上の Claude Code)、Claude for Excel です。加えて ZDR 組織では CORS が使えないので、ブラウザから直接呼ばずにバックエンドのプロキシ経由にします。

Fable 5 と Mythos 5 は ZDR で使えない

ZDR を検討するときに引っかかりやすいのがここです。Claude Fable 5 と Claude Mythos 5 は Covered Models に指定されていて、30 日のデータ保持が必須です。したがって ZDR では利用できません。Claude API で保持設定を満たさない組織から Fable 5 を呼ぶと、次のエラーが返ります。

{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "In order to access this model, your organization or workspace must have data retention enabled."
  }
}

逃げ道はワークスペース単位の設定です。ZDR の組織でも、特定のワークスペースだけ 30 日保持を有効にすれば、そのワークスペースから Fable 5 と Mythos 5 を呼べます。他のワークスペースは zero data retention のままです。Claude Code でも同じ制約があり、ZDR 組織では /model の一覧から Fable 5 が消えるか無効表示になり、best エイリアスは Opus へ解決されます。

この 30 日保持要件は提供先を問わず適用されます。Claude API と Claude Platform on AWS では Anthropic が保持し、Amazon Bedrock と Google Cloud の Agent Platform では保持データがクラウドプロバイダ側の環境に留まります。

Bedrock 側の ZDR 設定(未確認)

ここから先は一次情報の原文を確認できていません。執筆時のネットワークポリシーで aws.amazon.com と docs.aws.amazon.com への接続がブロックされ、AWS 公式ドキュメントと発表記事の本文を取得できなかったためです。以下は検索結果に現れた要約からの記述で、公式ドキュメントで裏取りしてください。

  • Amazon Bedrock はアカウント単位またはプロジェクト単位でデータ保持モードを設定でき、モードは none / default / inherit / provider_data_share の 4 つとされています
  • 組織横断で強制する場合は SCP で bedrock-mantle:DataRetentionMode 条件キーを使い、none 以外への設定を Deny します
  • 新規アカウントの既定は inherit なので、SCP を付けるだけでは none になりません。各アカウントで put-account-data-retention --mode none を明示的に呼ぶ必要があるとされています
  • Claude Opus 5 on Amazon Bedrock は既定で zero data retention である、と AWS の発表記事が述べているようです

「モードは上限であって下限ではない」という説明も見かけました。zero retention に対応するモデルは、アカウント設定にかかわらず zero retention で動く、という意味です。この挙動も含め、実際の設定前に Data retention - Amazon Bedrock を必ず確認してください。

結局どう理解しておけばよいか

ZDR は「保存しない」であって「送らない」ではない。誰が保存しないのかは Bedrock か Claude Platform on AWS かで変わる。ZDR でもフラグされた内容は最大 2 年残るし、Files API や Batches のような状態を持つ機能は最初から対象外。この 3 点を押さえておけば、社内で「ZDR だから大丈夫」と言われたときに、何が大丈夫で何が大丈夫でないかを切り分けられます。
