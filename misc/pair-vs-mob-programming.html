ペアプロとモブプロの違い、なぜモブへ発展したのか

いちばん見えやすい違いは人数(2 人か、チーム全員か)ですが、本質は 開発の判断をどの単位で行うかにあります。ペアプログラミングは 「コードを書く作業を 2 人でやる」開発プラクティスで、モブプログラミングは 「チームの作業と意思決定を、全員が同じ時間・同じ場所・同じ 1 台で行う」働き方そのものです。

モブへ発展した理由は、ペアにしても消えなかった質問待ち・レビュー待ち・引き継ぎを 工程ごと無くすためでした。2011 年に米 Hunter Industries の Woody Zuill のチームが、 coding dojo と TDD の練習の延長で偶然たどり着き、Agile2014 の Experience Report として世に出ています。

ペアプログラミングのおさらい

ペアプログラミングを世に広めたのは Extreme Programming (XP) です。Kent Beck は 1999 年の Extreme Programming Explained で、製品コードは 1 台のマシン、 1 つのキーボード、1 つのマウスを 2 人で見ながら書く、と定義しました。役割は キーボードを持つ driver と、少し先の方向を見る navigator に分かれます。

ただし XP が発明したわけではありません。Larry Constantine は 1995 年の Constantine on Peopleware で、2 人 1 組で驚くほど速く、バグの少ないコードを書く 開発者たちを "Dynamic Duos" として報告しています。同じ 1995 年に Jim Coplien が Pattern Languages of Program Design で "Developing in Pairs" パターンを 書き残しました。現場にあった観察を、XP がプラクティスとして規定したという流れです。

モブプログラミングの定義

Woody Zuill の言い方を借りると、モブプログラミングは 「チーム全員が、同じことを、同じ時間に、同じ場所で、同じコンピュータで行う」開発です。 キーボードを持つ driver は 1 人だけで、残りは全員 navigator になります。

ここで効いてくるのが、Llewellyn Falco の strong-style pairing の黄金律です。

アイデアが自分の頭からコンピュータへ入るには、必ず他の誰かの手を通らなければならない。

つまり driver は、セッション中で唯一「自分のアイデアを自分でコードにしない」人です。 思いついた人は口で説明するしかないので、全員が同じ理解に留まり続けます。driver は タイマーで交代し、10 分前後を目安にする現場が多いです(議論中はタイマーを止める運用もよく使われます)。

モブへ発展した理由

モブプログラミングは、誰かが机上で設計した手法ではありません。2011 年、Hunter Industries の チームが coding dojo(みんなで 1 台を囲んで練習する集まり)と TDD の練習を重ねるうちに、 その集団の進め方を実務のコードに持ち込んでみたのが始まりです。Zuill 自身、うまくいっていることに 注目してそれを増やす、いわゆる "turn up the good" を毎日繰り返した結果として生まれた、と 振り返っています。

ではペアで足りなかったのは何かというと、ペアの外側です。ペアを組んでも、仕様の判断を プロダクトオーナーに聞けば返事を待ちますし、別領域のコードを触ればその担当者を待ちます。 PR を出せばレビューを待ちます。この待ちの間、仕事は止まっているのに、人はそれぞれ別の仕事を 始めるので、着手中の仕事(WIP)だけが増えていきます。

チーム全員が同じ部屋で 1 台に向かっていれば、この待ちは原理的に発生しません。 判断できる人がその場にいて、その場で決まり、その場でコードになる。Hunter Industries の チームが手応えを感じたのはこの点で、質問の答えを待たなくてよく、全員が常に同じ文脈にいると すごく進む、という実感が出発点になっています。

ここは私なりの整理ですが、モブは「人の稼働率(resource efficiency)」を捨てて 「仕事が流れる速さ(flow efficiency)」を取る選択です。5 人が別々のタスクを持てば稼働率は 100% に見えますが、待ちと引き継ぎと手戻りが混ざるので 1 件が終わるまでは遅くなります。 モブは稼働率の見た目を犠牲にして、1 件を最短で終わらせにいきます。稼働率で管理している 組織ほどモブが受け入れられにくいのは、この評価軸のズレが理由です。

5 人がかりは無駄ではないのか

正直に書くと、「モブは常に速い」と言い切れる一次情報は、今のところ見当たりません。 2019 年の systematic literature review では、2 つの文献データベースを探しても対象になる 論文が 10 本しか見つからず、報告されている効果(コード品質の向上、生産性の向上)の多くは 経験報告と参加者アンケートに基づく主観的なもの、と整理されています。厳密な対照実験は ほとんど行われていません。

比較すると、ペアプログラミングのほうが実証研究は蓄積されています。Laurie Williams らが IEEE Software 誌に出した 2000 年の "Strengthening the Case for Pair Programming" は、 ペアのほうがより良いソフトウェアをより短時間で作り、開発者も自信を持てるようになったと 報告しました。もっとも、こうした効果が課題の難しさや開発者の熟練度に左右されることも 後年の研究で指摘されており、無条件に効くわけではありません。

なので、導入するなら「速くなるから」ではなく、知識の偏りをなくしたい、 引き継ぎで落ちる情報を無くしたいという目的で選ぶほうが、期待とのズレが小さいです。

使い分けの目安

モブが効きやすいのは、答えが一意に決まらない仕事です。新しい領域の設計判断、 誰も読めなくなったレガシーコードの解読、新メンバーのオンボーディング、障害の恒久対策など、 「決めるのが難しく、決めた理由を全員が知っておくべき」仕事と相性がいいです。

逆に、手順が確定している定型作業、機械的な一括修正、ひたすら調べ物をするフェーズは、 ソロかペアのほうが素直です。全員で 1 画面を見ても、待つ人が増えるだけになります。

呼び名について

英語の mob には「暴徒」の意味があるため、2020 年ごろから ensemble programming と呼び替えるコミュニティが増えました。 Maaret Pyhäjärvi の Ensemble Programming Guidebook がその代表です。 Zuill 自身は近年 software teaming という言い方を使っています。 指しているものは同じなので、日本語の記事や社内の会話では「モブプロ」で通じます。

まず試すなら

いきなり全業務をモブにする必要はありません。90 分だけ枠を取り、driver を 10 分交代にして、 実際に進めたい 1 件を選ぶところから始めるのがおすすめです。タイマーは mobti.me のような Web ツールでも、手元のコマンドでも構いません。

# 10 分ごとに交代の合図を出すだけの簡易タイマー(macOS / Linux)
while true; do sleep 600; echo "交代してください"; done

1 回やって「遅い」と感じても、それは想定どおりです。全員の理解が揃うまでの初回コストが 乗るので、2 回目以降と、その後に発生しなかった質問やレビューの往復まで含めて評価してください。
