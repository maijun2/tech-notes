Windows の Kiro Crew で Computer Use を使うとき、Node などの追加インストールは必要か

PowerPoint やエクスプローラといった ネイティブ Windows アプリを操作するだけなら、追加インストールは不要です。Settings → Computer Use を ON にするだけで動きます。Windows ドライバは UI Automation を raw ctypes COM で直接呼ぶ実装(comtypes すら使わない)で、Node.js にも外部ランタイムにも依存しません。

ただし ブラウザだけは話が別です。Kiro Crew の Browser 機能は playwright-cli を叩く仕組みなので、Node.js 20 以上と @playwright/cli のグローバルインストール、そして Chromium の取得が必要になります。ブラウザ操作を Computer Use だけで済ませることも可能ですが、速度と安定性は Browser 機能に劣ります。

前提: インストール形態によって「もともと必要なもの」が違う

まず Computer Use の話に入る前に、Kiro Crew 本体のインストール形態を押さえておきます。Windows ネイティブには 2 つの導入パスがあり、前提ソフトが異なります。

形態 Python Node.js その他
デスクトップインストーラ(署名済み KiroCrew-Setup.exe) 不要(backend 同梱) 不要 Kiro CLI(kiro-cli)は別途
ソースインストール(ネイティブ) 必須(3.12〜3.13、Windows の検証済みは 3.12) 任意 Git for Windows、kiro-cli

デスクトップインストーラは backend をバンドルしているため、公式ドキュメントも「no separate Python install needed」と明記しています。ソースインストールの場合の Node.js は React dashboard をビルドするための任意の前提で、入れなければ gateway が prebuilt bundle を配信します。つまり Node.js は、この時点ではどちらの形態でも必須ではありません。

なお、どちらの形態でも Kiro CLI のインストールとサインインは人間が自分で行う必要があります。Kiro Crew は既定のチャット backend を Kiro CLI に委譲する設計で、リモートインストーラのダウンロードもログインプロセスの起動もしません。

# ソースインストールの最小手順(PowerShell)
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -e ".[voice]"

kirocrew setup
kirocrew gateway

Computer Use 本体: ON にするだけで追加インストールはない

Computer Use は既定で OFF です。有効化は dashboard の Settings → Computer Use から行い、実体は ~/.kiro/crew/computer_use.json という 1 ファイルです。これは agent が読み書きできない場所に置かれた「keystone(要石)」で、ファイルが無い・壊れている・"enabled": "false" のような型違いの場合はすべて 無効に倒れます。

{ "enabled": false, "allowed_apps": [], "extra_denied_apps": [] }

Windows のドライバは UIAutomationCore を raw ctypes COM 経由で呼び、画面キャプチャは PrintWindow / GDI+ を使います。仕様書には「UIAutomationCore over raw ctypes COM (no comtypes)」と書かれており、pip の追加パッケージすら挟んでいません。したがって PowerPoint、Excel、エクスプローラ、設定アプリといったネイティブアプリの読み取り(computer_list_apps / computer_get_state)と入力(click / type / set value / scroll)は、Computer Use の ON 以外に何も要りません。

要素を指定した操作は UI Automation の control pattern を通るため、あなたのマウスカーソルもキーボードフォーカスも奪いません。これが click_method: "auto" の解決先です。

ブラウザだけは Node.js 20 以上が必要

Kiro Crew の Browser 機能は Playwright の agent CLI である playwright-cli を、agent の通常のコマンドパス上で実行する仕組みです。プラットフォーム要件として Node.js 20 or newer が明記されています。

# Browser 機能のインストール(gateway が自動実行する内容)
npm install -g --prefix <data-home>/playwright-cli @playwright/cli@latest
playwright-cli install-browser chromium

ポイントは 3 つです。

  • グローバルインストールのみ。npx は実行のたびに npm registry を引き直すため、トークン失効でセッション中に機能が落ちる。グローバルなら registry 認証はインストール時だけで済む
  • PATH は参照されない。gateway は <data-home>/playwright-cli 配下、次に書き換え不可能な固定システムパスの launcher だけを採用し、そこに native な Node 実行ファイルを封じ込めて直接呼ぶ
  • 企業 PC 向けの逃げ道はある。playwright-cli.ps1(Windows 用の standalone installer)は、要件を満たす Node が無ければ公式リリースを SHA-256 検証付きで取得して Node を bootstrap します。人間が手で実行するもので、製品側からは呼ばれません

ではブラウザも Computer Use で操作すればいいのでは?

技術的には可能です。Chrome や Edge のウィンドウも UI Automation から見えるので、Node.js を入れずに Computer Use だけでブラウザを触れます。ただし コストが大きい点は理解しておくべきです。仕様書には実測値として、実際の Chromium ウィンドウで 1200 ノードの予算に達するまで 約 630ms(Windows の walk は macOS より明確に遅い)、状態を変える操作は 2 回 walk する、と書かれています。フォーム入力やページ取得の反復には向きません。

Windows 固有の制限(事前に知っておきたい点)

Node の有無とは別に、Windows の Computer Use には macOS と異なる制約があります。いずれも公式ドキュメントに明記された仕様です。

  • 昇格していない gateway は昇格ウィンドウを読めません(UIPI)。secure desktop はどのアプリからも到達不能で、これは仕様であって不具合ではありません
  • swapchain で描画されるウィンドウはキャプチャできません。Windows Terminal はスクリーンショット無しのツリーだけが返ります
  • type_text / press_key はキーボードフォーカスを奪います。Windows にはプロセス単位の入力配送(macOS の CGEventPostToPid 相当)が無いためです。結果にもその旨が明示されます
  • 座標クリックは click_method: "global" の明示指定が必要です。実カーソルが動くため、auto はこれを解決先に選びません
  • ツリーの walk が遅いため、max_tree_nodes の引き上げは慎重に

あわせて注意: Windows には OS サンドボックスが無い

Computer Use とは直接関係しませんが、Windows ネイティブ環境を選ぶ際に一番効いてくる差分です。Kiro Crew の OS レベルサンドボックス(Linux の user namespace、macOS の sandbox-exec)は Windows に存在せず、インストールして解決できるものもありません。

チャット本体は Kiro CLI 内蔵のサンドボックスに委譲されるので問題ありませんが、スクリプト、hooks、サードパーティ ACP backend、MCP プローブ、gh/glab といった経路は 既定で unconfined(無拘束)で実行されます。これは「有効化してしまったバイパス」ではなく、このプラットフォームの文書化された既定値です。拒否したい場合は %USERPROFILE%\.kiro\crew\config.json で明示します。

{ "agent": { "sandbox_allow_unsandboxed_exec": false } }

ただしこの設定を入れると、MCP サーバ、app backend、script cron、hooks などがサンドボックスエラーで失敗するようになります。現在の状態は kirocrew doctor の Sandbox 欄で確認できます。

PowerPoint 資料を「作る」用途なら別の選択肢もある

Kiro Crew には PPTX Maker という、チャットから実際の .pptx を生成する組み込みアプリがあります。ただし対応プラットフォームは macOS と Linux のみです(エンジンの toolchain が POSIX の venv レイアウトを前提としているため、Python 自体は Windows でも import できるが manifest 側で抑止されている)。

したがって Windows ネイティブ環境では、PowerPoint に関しては 実際の PowerPoint アプリを Computer Use で操作する形になります。この用途に追加インストールは不要です。

まとめ

  • Computer Use を ON にするだけ → 追加インストール不要(PowerPoint、Excel、エクスプローラ等)
  • Browser 機能でブラウザを操作 → Node.js 20 以上 + @playwright/cli + Chromium が必要
  • ブラウザを Computer Use で代用 → Node 不要だが walk が遅く、反復作業には不向き
  • デスクトップインストーラなら Python も不要。ソースインストールなら Python 3.12 が必須
  • いずれの場合も kiro-cli のインストールとサインインは自分で行う
